# База данных

Supabase (PostgreSQL). Схема и правила доступа — миграции в `supabase/migrations/`:
`20261104201500_objects_tasks.sql` (схема, триггеры, RPC, RLS) и
`20261104204500_change_task_status_comment.sql` (уточнение RPC: пустой комментарий, код ошибки).
Защита работает в базе, поэтому действует и при запросах в обход интерфейса.

## Схема

| Таблица | Что хранит |
|---|---|
| `profiles` | пользователь: `id` (= `auth.users.id`), `full_name`, `role` — `manager` (постановщик) или `executor` (исполнитель) |
| `objects` | стройка: `name`, `address`, `created_by`, `created_at` |
| `tasks` | задача: `title`, `description`, `object_id`, `assignee_id`, `status`, `author_id`, `created_at`, `updated_at` |
| `task_history` | смена статуса: `task_id`, `actor_id` (кто), `from_status`, `to_status`, `comment`, `created_at` (когда) |

Статус — enum `task_status`: `new` (Новая), `in_progress` (В работе), `review` (На проверке),
`accepted` (Принята), `rework` (На доработке).

## Переходы статусов

Только через RPC `change_task_status(p_task_id, p_to, p_comment)`:

| Из | В | Кто | Условие |
|---|---|---|---|
| — | Новая | постановщик | при создании задачи (статус ставит база) |
| Новая | В работе | назначенный исполнитель | |
| В работе | На проверке | назначенный исполнитель | |
| На проверке | Принята | постановщик | |
| На проверке | На доработке | постановщик | комментарий обязателен (одни пробелы, табуляции и переводы строк не считаются) |
| На доработке | В работе | назначенный исполнитель | |

Остальные переходы RPC отклоняет ошибкой. Каждый переход пишет строку в `task_history`.

## Как устроена защита

- **RLS на всех таблицах.** Постановщик видит всё. Исполнитель видит только свои задачи, их историю
  и объекты, где у него есть задачи. Пользователь без профиля и `anon` не видят ничего.
- **Запись.** Объекты и задачи создаёт, правит и удаляет только постановщик. Исполнитель меняет
  задачу только через RPC смены статуса.
- **Статус** нельзя поменять обычным UPDATE: триггер `tasks_guard` пропускает смену статуса только
  из RPC. RPC работает от владельца базы (`security definer`, `search_path=''`) и сам проверяет
  переход, роль и то, что задача назначена этому исполнителю.
- **Правила правки задачи** (триггер `tasks_guard`): при создании база сама ставит статус «Новая»,
  автора (текущий пользователь) и дату. Принятую задачу изменить нельзя. Исполнителя можно сменить
  только в «Новая» и «На доработке». Исполнителем может быть только пользователь с ролью «Исполнитель».
  Автор и дата создания не меняются. Удалить задачу можно только в «Новая».
- **Объект с задачами** удалить нельзя: внешний ключ `tasks.object_id` с `on delete restrict`.
- **История.** У клиентов нет прав на insert, update и delete в `task_history`. Записи пишут только
  триггер создания задачи и RPC.
- **Регистрация** закрыта в настройках Auth (`disable_signup`), анонимный вход выключен.
- **Ключи.** Фронту нужны только URL проекта и anon key. `service_role` и личный токен
  Management API лежат только локально в `.env.local`, файл в `.gitignore`.

## Скрипты

Нужен Node 20.12+, npm-зависимостей нет. Переменные — в `.env.local` в корне: `SUPABASE_URL`,
`SUPABASE_PROJECT_REF`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ACCESS_TOKEN`
(личный токен supabase.com → Account → Access Tokens).

| Команда | Что делает |
|---|---|
| `npm run db:migrate` | применяет новые файлы из `supabase/migrations` через Management API. Каждый файл и запись в журнал `supabase_migrations.schema_migrations` идут одной транзакцией. Применённые файлы пропускаются. Файл не должен содержать BEGIN/COMMIT |
| `npm run db:seed` | создаёт 1 постановщика и 2 исполнителей (`manager@`, `executor1@`, `executor2@example.com`), 3 объекта и 8 задач во всех статусах. Статусы проводятся через RPC под токенами пользователей, поэтому история настоящая. Повторный запуск ничего не дублирует. Пароли печатаются одной таблицей в конце: новым пользователям — сгенерированные, существующим не меняются. `npm run db:seed -- --reset-passwords` выдаёт новые пароли всем |
| `npm run db:check` | проверка безопасности: прямые запросы к REST, RPC и Auth под `anon`, под каждым пользователем и под пользователем без профиля. Отдельно проверяется, что значений `service_role` и токена Management API нет в файлах репозитория и в `web/dist`, а ключ для фронта имеет роль anon. Каждое правило выводится отдельной строкой PASS/FAIL, код выхода 1 при любом FAIL. Скрипт меняет только свои временные записи с префиксом `[security-check]` и удаляет их в конце |

Порядок для нового проекта: в Auth выключить регистрацию, затем `db:migrate`, `db:seed`, `db:check`.
